How the kit works

Claude Code reads a few kinds of files from your project. The kit uses each for what it's best at: instructions that always apply, rules that apply to certain files, commands you start with a slash, agents Claude hands work to, settings that enforce safety, and plain documents that hold your project knowledge.

PartWhereWhen Claude Code loads it
InstructionsCLAUDE.md and the files it imports with @At the start of every session
Rules without paths:.claude/rules/*.mdEvery session
Rules with paths:.claude/rules/**/*.mdWhen Claude reads or edits a matching file
Commands (skills).claude/skills/<name>/SKILL.mdName and description always (unless only you can run it); full text when it runs
Agents.claude/agents/<name>.mdName and description always; full text when Claude delegates to it
Settings.claude/settings.jsonApplied by Claude Code itself; enforced, not just advice
Documentsdocs/sdlc/Only when a task needs them (except the two imported by CLAUDE.md)

This keeps every conversation light: only about 250-300 lines are always loaded, and everything else arrives when it's relevant. One important difference: instructions and rules are guidance that Claude follows; settings (permissions and hooks) are enforced by Claude Code. That's why the kit blocks secrets with permission rules rather than a sentence in CLAUDE.md.

Quick start

  1. Generate your kit with the Claude Code SDLC Generator.
  2. Project ZIP: unzip it into your project's root folder, on a new git branch. Plugin: unzip it into ~/.claude/skills/sdlc-kit/, then run /sdlc-kit:setup in each project.
  3. Open Claude Code in the project and run /sdlc-init (plugin: /sdlc-kit:sdlc-init). Answer its questions.
  4. Check the sections it marked as inferred, then commit the kit so your team shares it.

Filling in the docs

Every document section starts with a hint in an HTML comment, which you replace with your own words:

## Who uses it
<!-- FILL: the main users and what they need. Example (fictional): "Shop owners creating invoices on their phone." -->
You seeIt meansWhat Claude does
<!-- FILL: … -->Not filled inWorks it out from the code and labels it, asks you if it matters, never invents it
<!-- INFERRED: … -->Written by Claude, not confirmedUses it but says it's inferred. Check it, then delete the marker
Plain textWritten or confirmed by a personTreats it as your intent and never overwrites it without asking
"A good default" in a hintA recommended practiceFollows it until you write your own

Examples inside hints are always fictional (an invoicing app), and a rule tells Claude never to treat them as facts about your project. In the generator's preview, files with sections to fill are marked ✎.

CLAUDE.md, quick start and settings

CLAUDE.mdEvery kit

Project instructions

What it does
The instructions Claude reads at the start of every session in your project: how to work here, the build and test commands, project-specific rules, the list of docs and the list of commands.
How it works
Claude Code loads CLAUDE.md from the project root automatically. Lines starting with @ (such as @docs/sdlc/00-project-overview.md) import another file, which is loaded at the same time. The kit keeps this file short (well under the 200 lines the docs recommend), because everything in it uses context on every turn; detailed knowledge lives in docs/sdlc/ and is read only when a task needs it.
What you can change
  • Fill in Build, run and test with your exact commands. This is the single most useful edit.
  • Add your own always/never rules under Project-specific rules, one per line.
  • Remove rows for docs or commands you deleted.
  • If you already had a CLAUDE.md, the kit is generated as CLAUDE.sdlc.md; add the line @CLAUDE.sdlc.md to your file to load it.
  • Personal notes that shouldn't be shared go in CLAUDE.local.md (add it to .gitignore).

SDLC-QUICKSTART.mdEvery kit

Quick start for people

What it does
A one-page guide for your team: the first 10 minutes, every command in your kit, how the fill-in markers work, what each folder contains and how to customise it.
How it works
Claude doesn't load it automatically; it's for humans. It is generated to match your choices, so it lists exactly the commands and agents in your kit.
What you can change
  • Share it with new team members, or link it from your README.
  • Delete it once everyone knows the kit; nothing depends on it.
.claude/settings.jsonEvery kit

Safety settings

What it does
Permission rules shared by everyone on the project. Claude can't read or edit .env files (except .env.example, .env.sample and .env.template), keys and certificates (*.pem, *.key, *.p12, *.pfx, *.jks, SSH keys) or anything in a secrets/ folder, and it asks before git push, git reset --hard and git clean. If you entered a format or lint command, it also contains a Stop hook that runs it each time Claude finishes a reply.
How it works
Read(…) and Edit(…) deny rules block Claude's file tools and also common shell commands that name the file, such as cat .env. A rule starting with ! carves an exception out of the rules before it. Ask rules make Claude Code ask you before running a matching command. Settings in this file are shared through git; your personal overrides go in .claude/settings.local.json.
What you can change
  • Add paths to deny, e.g. "Read(config/credentials.yml)".
  • Allow commands you approve often, e.g. "allow": ["Bash(npm run test *)"], so Claude stops asking.
  • Change or remove the lint hook under hooks.Stop; on Windows without Git Bash add "shell": "powershell" to the hook.
  • For OS-level protection that also stops scripts reading secrets, enable Claude Code's sandbox (see the permissions docs).

.claude/rules/how-to-use-sdlc-docs.mdEvery kit

Using the SDLC docs

What it does
Teaches Claude the fill-in markers: an empty <!-- FILL --> section means "unknown", <!-- INFERRED --> means "written by Claude, not yet confirmed", plain text means "confirmed by a person". It tells Claude to look in the code first, ask when it matters, never invent facts, never overwrite text a person wrote, and treat the examples in FILL comments as fictional.
How it works
Rules in .claude/rules/ without a paths: header load in every session, like an extension of CLAUDE.md. This one is short on purpose.
What you can change
  • Usually nothing. Change it only if your team wants a different marker convention.

.claude/rules/research-and-sources.mdEvery kit

Research and sources

What it does
Makes Claude back technical claims with sources: your own code first (cited as path:line), then official documentation for the versions you actually use, then standards bodies, then well-known references. It must only cite pages it opened in the session, give a confidence level, and show disagreements between sources.
How it works
Loaded in every session. The /research command and the researcher agent follow it in detail.
What you can change
  • Add your company's internal documentation as the first trusted source.
  • Tighten or relax the citation format.

.claude/rules/security.mdEvery kit

Security basics

What it does
Ten short security rules based on the OWASP Top 10 and ASVS: no secrets in code or logs, validate input at the boundary, parameterised queries, output encoding, server-side access checks, safe file paths, careful errors and logs, justified dependencies, no disabled TLS checks.
How it works
Loaded in every session, so every change Claude makes is held to these basics. Deeper reviews are done by the security-reviewer agent.
What you can change
  • Add your own rules, e.g. "all endpoints require the @Secured annotation".

.claude/rules/coding-standards.mdDeveloper

Coding standards

What it does
General coding standards: put code where similar code lives, small focused functions, no duplicated logic, deliberate error handling, validation at the boundary, no unrequested dependencies, focused changes, tests for new behaviour, and updating the API and architecture docs when they change.
How it works
It has a paths: header (src/**, app/**, lib/**, packages/**, cmd/**, internal/**, pkg/**), so Claude Code loads it only when Claude reads or edits a matching file, which saves context in other tasks.
What you can change
  • Change the paths: globs to match your source folders, e.g. "backend/**".
  • Add your team's conventions (naming, patterns, forbidden libraries).

.claude/rules/testing-standards.mdTester

Testing standards

What it does
How good tests look: one behaviour per test, independent, deterministic (no fixed sleeps), meaningful assertions, stable UI locators, test case IDs in test names. What never to do (weaken tests to pass, use real personal data, load-test production without permission) and how to classify a failure.
How it works
Path-scoped to test folders and test files (src/test/**, tests/**, e2e/**, **/*.spec.*, …) and to docs/sdlc/testing/**.
What you can change
  • Add your test folders to paths: if they're named differently.
  • Add team rules, e.g. "every API test checks the error format".

Slash commands

Each command is a folder in .claude/skills/ with a SKILL.md file: a short YAML header (name, description, optional settings) and the instructions Claude follows. Typing /name runs it; text after the name is passed in as $ARGUMENTS. Commands that change code, commit or write many files have disable-model-invocation: true, so only you can start them. Some run in a separate context (context: fork) and return only a summary.

---
name: test-cases
description: Design test cases for a user story from its acceptance criteria…
argument-hint: "<story ID or story text>"
context: fork
agent: test-designer
---

# Test cases

Story: $ARGUMENTS

/sdlc-init [area]

What it does
The first command to run. Reads your project (build files, README, CI, Docker, config, tests, a few central source files), fills empty doc sections it can prove from the code (marked inferred), fills the build commands in CLAUDE.md, then asks you up to 5 questions about what it can't work out, and writes your answers back.
How it works
It edits only CLAUDE.md and docs/sdlc/, never code. It never overwrites text you wrote; conflicts between docs and code are listed in its report. Run it again any time.
What you can change
  • Add files it should always read for your stack (e.g. nx.json).

Subagents

Claude hands a task to an agent when the task matches the agent's description, or when you ask: "use the code-reviewer agent", or type @ and pick it. Agents work in their own context and report back, which keeps your conversation focused. Tool lists keep reviewers read-only.

tools: Read, Grep, Glob, Bash
disallowedTools: Write, Edit
memory: project

Workspace edition (several services)

For microservices and other multi-repository setups. Instead of installing the kit in every service, clone all your services into one folder and put the kit at its root. Open Claude Code in that folder and it sees every service, so one setup covers them all and Claude can follow a change from one service to the next.

my-platform/                 ← open Claude Code here
├── CLAUDE.md, .claude/, docs/sdlc/   (the kit, shared by all services)
├── services.txt, clone-services.sh/.ps1, .gitignore
├── order-service/           ← its own git repository
├── payment-service/         ← its own git repository
└── web-app/                 ← its own git repository

Claude Code loads CLAUDE.md from the folder you start in and its parent folders, and finds settings, commands and agents in the start folder only. That's why you always start at the workspace root. A service's own CLAUDE.md, if it has one, still loads when Claude works on files in that service. To share the workspace, run git init at the root and push it as its own repository; the .gitignore keeps the services out, and teammates clone it and run the clone script.

Clone scripts

What it does
Clones every service in services.txt that isn't in the workspace yet. Use ./clone-services.sh on macOS, Linux or Git Bash and .\clone-services.ps1 in PowerShell.

Skips folders that already exist and never pulls or changes existing clones, so it's safe to run any time. Each service stays its own git repository with its own branches and history.

Plugin edition

The plugin edition packs the same commands and agents as a Claude Code plugin named sdlc-kit, installed once for all your projects. Plugins can ship commands (skills/), agents (agents/) and hooks (hooks/hooks.json), but not CLAUDE.md, rules or permission settings, so those are in templates/ and /sdlc-kit:setup copies them into each project. Commands are used as /sdlc-kit:<name> and agents as sdlc-kit:<name>.

Customise the kit

Add your own command

Create .claude/skills/deploy-check/SKILL.md. The folder name becomes the command; keep the description specific, because Claude uses it to decide when the command fits.

---
name: deploy-check
description: Check that a branch is ready to deploy: tests pass, migrations are reversible, no TODOs in changed files.
argument-hint: "[branch]"
disable-model-invocation: true
---

Check branch $ARGUMENTS:
1. …

Add or narrow a rule

Add a file to .claude/rules/. Give it a paths: header so it loads only for the files it's about, which keeps every other conversation lighter.

Add an agent

Create .claude/agents/<name>.md with name, a description that says when to use it ("use proactively when…"), a tools list (as small as possible) and its instructions.

Allow commands you trust, block files you don't

{
  "permissions": {
    "allow": ["Bash(npm run test *)", "Bash(./mvnw test *)"],
    "deny": ["Read(.env)", "Read(config/credentials.yml)"]
  }
}

Run a formatter automatically

{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "npm run lint -- --fix", "shell": "bash" } ] }
    ]
  }
}

Use "shell": "powershell" on Windows without Git Bash. A PostToolUse hook with "matcher": "Write|Edit" runs after every file edit instead.

Remove what you don't need

Delete a command's folder or an agent's file and remove its row from CLAUDE.md. Fewer commands and agents that Claude can start on its own means a lighter context on every turn and fewer wrong picks.

Check your setup

Run /doctor prompt-audit in Claude Code to find conflicting or outdated instructions across CLAUDE.md, rules, commands and agents.

Troubleshooting

ProblemFix
A command doesn't appearCheck the path is .claude/skills/<name>/SKILL.md, that name matches the folder, and that the YAML header is valid: a description containing ": " must be quoted. Start a new session after adding files.
Claude ignores an instructionKeep CLAUDE.md short and free of contradictions; run /doctor prompt-audit. For things that must never happen, use permission rules or hooks, which are enforced.
An agent is never usedMake its description say when to use it ("use proactively when…"), or ask for it by name, or type @ and pick it.
A hook doesn't run on WindowsAdd "shell": "powershell" to the hook, or install Git Bash.
Scripts can still read secretsDeny rules cover Claude's file tools and shell commands that name the file, not programs that open files themselves. Enable Claude Code's sandbox for OS-level protection.
Plugin commands are missingCheck .claude-plugin/plugin.json exists in the plugin root, look at the Errors tab in /plugin, and run /reload-plugins.

Frequently asked questions

Can I use one kit for several microservices?

Yes. Choose the workspace edition, clone all your services into one folder, unzip the kit at the root of that folder and always open Claude Code there. Each service stays its own git repository; the workspace can be shared as a separate small repository with a clone script.

Do I have to fill in every document?

No. The kit works unedited. Empty sections are marked with FILL comments; Claude works them out from your code when it needs them and asks you only about things the code can't tell it, such as who your users are. Filling in the project overview and the build commands gives the biggest improvement.

Which files are loaded in every Claude Code session?

CLAUDE.md, the two docs it imports (project overview and folder structure), the rules without a paths header (using the docs, research and sources, security), and the names and descriptions of the commands and agents Claude can use on its own. Everything else loads only when it's needed.

What is the difference between a command and an agent?

A command (skill) is a set of instructions you start with a slash, such as /implement, and it runs in your conversation. An agent (subagent) is a specialist with its own instructions and tools that Claude hands a task to, and it works in its own context and reports back.

Why can some commands only be run by me?

Commands that change code, commit, create pull requests or write many files have disable-model-invocation set, so Claude never starts them on its own. Read-only commands such as /explain and /review-changes can also be used by Claude when they fit your request.

Can I use the kit with other AI coding tools?

The docs in docs/sdlc are plain Markdown and useful to any tool or person. CLAUDE.md, rules, skills, agents and settings use Claude Code's formats. Claude Code can also read an AGENTS.md file if your other tools use one.

How do I update the kit later?

Generate a new kit with the same choices and compare it with your files, or update the plugin edition and run its setup command again. Your own edits stay in your files; nothing overwrites them automatically.
